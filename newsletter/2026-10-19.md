> 편집 노트 — 연결한 도구의 수보다 중요한 질문이 있습니다. 무엇을 검사하지 못했나요? 어디서 느려졌나요? 사람의 승인을 기다리나요? 001호 이후 나온 릴리스에서 이 질문에 답하는 변화를 골랐습니다. 발표일과 오늘의 확인일은 다릅니다.

## 이번 호, 세 줄 요약

- **Skills:** 스캔 결과에 ‘검사하지 못한 대상’이 포함되는지 확인하세요.
- **MCP:** 화면 녹화와 성능 진단을 함께 남겨 완료 보고에 근거를 붙이세요.
- **Harness:** 오래 실행되는 작업에서 승인 대기와 실패를 구분하세요.

<a id="skills"></a>

## 01 / Skills — 검사 누락도 결과입니다

**발표:** 2026-10-15 한국 시간 · **대상:** Skill Scanner·스킬 배포 CI 사용자 · **판단:** 업데이트와 CI 규칙 검토

**사실:** Skill Scanner 2.3.0은 따라가지 않은 심볼릭 링크를 `SYMLINK_NOT_SCANNED`, `scan-all`에서 로드하지 못한 스킬을 `SKILL_LOAD_FAILED`로 보고합니다. 분류 코드와 YAML frontmatter 검사도 바뀌었습니다. [원본 릴리스](https://github.com/cisco-ai-defense/skill-scanner/releases/tag/2.3.0)

**의미 — 편집 의견:** 탐지 건수만 줄었다고 더 안전해진 것은 아닙니다. 검사 범위가 줄어도 같은 결과처럼 보일 수 있습니다.

**다음 행동:** 고정된 스킬 묶음으로 변경 전후 결과를 비교하고, 미검사·로드 실패 항목을 따로 검토하세요. 새 finding과 분류 코드 변경이 기존 SARIF 필터·`--fail-on-severity` 종료 코드에 미치는 영향도 확인하세요. 통과는 안전 보장이 아닙니다.

<a id="mcp"></a>

## 02 / MCP — ‘동작합니다’에 진단 근거를 붙이세요

**발표:** 2026-10-15 한국 시간 · **대상:** Chrome DevTools MCP로 웹을 검증하는 개발자 · **판단:** 진단 흐름에 시험 도입

**사실:** Chrome DevTools MCP 1.11.0은 FFmpeg 없이 동작하는 screencast 도구를 기본 활성화하고, `performance_start_trace`에 `ignoreCache`를 추가했습니다. `lighthouse_audit`는 실패한 감사 항목과 DOM 노드를 결과에 직접 포함합니다. [원본 릴리스](https://github.com/ChromeDevTools/chrome-devtools-mcp/releases/tag/chrome-devtools-mcp-v1.11.0)

**의미 — 편집 의견:** 화면을 통과했다는 설명보다 재현 영상과 진단 결과가 리뷰에 유용합니다. 캐시 조건이 다르면 성능 비교도 달라집니다.

**다음 행동:** 민감한 계정이 없는 시험 브라우저에서 화면 하나를 골라 재현 단계·녹화·감사 결과를 함께 남기세요. 전후 비교에는 캐시 조건을 명시하고, 녹화·네트워크 자료에 개인정보나 토큰이 섞이지 않았는지 검토하세요. 녹화가 테스트 assertion을 대신하지는 않습니다.

<a id="harness"></a>

## 03 / Harness — 멈춘 것과 기다리는 것을 구분하세요

**발표:** 0.7.26은 2026-10-16, 0.7.27·0.7.28은 2026-10-17 한국 시간 · **대상:** Deep Agents 비동기 서브에이전트·ContextHubBackend 사용자 · **판단:** 관측·경로 회귀 테스트

**사실:** Deep Agents 0.7.26은 비동기 서브에이전트의 사람 대기 상태와 부모 아래의 trace를, 0.7.27은 메인 에이전트로의 상태 업데이트를 추가했습니다. 0.7.28은 `ContextHubBackend.glob`이 `path`를 따르도록 수정합니다. [0.7.26](https://github.com/langchain-ai/deepagents/releases/tag/deepagents%3D%3D0.7.26) · [0.7.27](https://github.com/langchain-ai/deepagents/releases/tag/deepagents%3D%3D0.7.27) · [0.7.28](https://github.com/langchain-ai/deepagents/releases/tag/deepagents%3D%3D0.7.28)

**의미 — 편집 의견:** 승인 대기를 시간 초과로 처리하면 같은 작업을 중복 실행할 수 있습니다. 진행 표시뿐 아니라 운영 판단에도 상태 구분이 필요합니다.

**다음 행동:** 사용하는 SDK 버전을 고정하고, 승인 대기·완료·실패를 구분해 기록하는 시험을 만드세요. 해당 백엔드를 쓴다면 하위 경로의 glob 결과도 회귀 검사하세요. 상태 알림과 경로 수정이 권한 강제를 대신하는 것은 아닙니다.

## 하나만 살펴본다면 / Chrome DevTools MCP

**용도:** 웹 구현 뒤 ‘왜 느린지, 무엇이 실패했는지’를 증거로 설명해야 할 때. 새로 출시된 프로젝트라는 뜻은 아닙니다.

이미 있는 브라우저 조작 도구를 모두 교체하기보다, 성능·네트워크 진단이 필요한 작업에서 추가 후보로 검토하세요. [카탈로그의 MCP](../catalog/README.md#mcp)에서 동작 자동화 도구와 역할을 비교할 수 있습니다. 이번 호는 성능 순위나 채택 보증이 아닙니다.

<a id="experiment"></a>

## 이번 호의 작은 실험 / 근거가 남는 웹 검증

조합: **프로젝트의 검증 기준 + Chrome DevTools MCP + 승인 경계**.

1. 자신이 관리하는 비민감 시험 페이지에서 사용자 흐름 하나와 기대 결과를 정합니다.
2. 같은 재현 단계와 캐시 조건으로 동작을 확인하고, 녹화·성능 진단·실패 항목을 수집합니다.
3. 공유 전에 민감정보를 점검하고, 관측한 결과와 아직 확인하지 못한 범위를 분리합니다.

**첫 요청 예시**

> 이 시험 페이지의 첫 화면에서 검색 결과까지 흐름을 검증해 주세요. 재현 단계, 기대 결과와 실제 결과, 캐시 조건, 녹화·진단 근거를 정리해 주세요. 파일 수정·외부 전송·배포는 하지 마세요. 로그인이나 민감정보를 만나면 중단하고 알려 주세요.

**완료 기준:** 재현 단계, 기대·실제 결과, 버전·캐시 조건, 근거 파일 위치, 실패·미확인 항목. 이 절차 자체는 실행 검증 결과가 아닙니다.
